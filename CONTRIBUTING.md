# Contributing to acme-ts

Thank you for your interest in contributing to `acme-ts`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the repository is an npm workspace locked with `package-lock.json`)
- Java, for the DynamoDB tests (they start [DynamoDB Local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html); GitHub's Ubuntu runners have it)

### Installation

```bash
git clone https://github.com/PeculiarVentures/acme-ts.git
cd acme-ts
npm ci
npm test
npm run build
```

## Project Layout

- `packages/<name>/` is one package: `protocol` (`@peculiar/acme-protocol`), `jose` (`@peculiar/jose`), `core`, `data`, `data-memory`, `data-dynamodb`, `server`, `server-express` (`@peculiar/acme-express`), `server-ra` (`@peculiar/acme-ra`) and `client`. The others are `@peculiar/acme-<name>`.
- `packages/test-server/` is a private example server used by the tests; `tsdown.config.ts` excludes it, so it is not built or published.
- `packages/<name>/src/index.ts` is the package's only public entry point and must stay aligned with its `exports`.
- `tsdown.config.ts` at the repository root builds every package (tsdown `workspace` mode). There are no per-package build configs.
- `tsconfig.json` at the root is used for typechecking, tests and the declaration build. Its `paths` map every package to its `src`, so packages and tests use the sibling sources without building them first.
- `packages/<name>/build/` is generated by `npm run build` and is not committed.

## Development Workflow

### Code Quality

Before opening a pull request, run from the repository root:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks every package with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report, and `npx vitest run packages/<name>` to run one package's tests.

### Testing

- Use Vitest: import `describe`, `it` and `expect` from `vitest` (globals are off) and assert with `expect`, not `node:assert`. The Reflect polyfill is loaded by `vitest.config.ts`.
- Put tests next to the code they cover as `*.spec.ts`.
- Cover new behavior and bug fixes with tests. For protocol changes, check the response status, the problem `type` and the returned objects.
- `packages/data-dynamodb` tests start DynamoDB Local (they need Java). `packages/client/src/lets_encrypt.spec.ts` calls the Let's Encrypt staging server.

### Build And Package Exports

Every package is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown builds `src/index.ts` into `build/index.js` with `.d.ts` declarations. Output is unbundled, so every source module is emitted under `build/` mirroring `src/`, but only the root entry is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in each `packages/<name>/package.json` are generated by tsdown on every build and must not be edited by hand. CI fails if the build changes a `package.json`.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the packages keeps working on supported Node.js versions. Use `import type` for type-only imports (`verbatimModuleSyntax`). Import CommonJS dependencies the way Node.js ESM exposes them (for example `import dynamoose from "dynamoose"`), and check new imports from the packed packages: Vitest is more lenient than Node.js.

`tsconfig.json` keeps `useDefineForClassFields: false`: the model constructors assign their params in the base class, and native class fields would reset them.

Packages have `"sideEffects": false`, except `acme-core`, whose logger modules load the Reflect polyfill and register the default logger at import time. Services are registered by the `DependencyInjection.register()` functions, not on import; keep it that way.

### Dependencies

- `tsyringe` is a **peer** dependency (and a dev dependency) of every package that registers into or resolves from its global `container`: the app registers into the same container, so it must have only one copy.
- `@peculiar/x509` is a **peer** of the packages that use its `cryptoProvider` or pass its objects across the API, and `@peculiar/asn1-schema` of the packages that import it (x509 3 has it as a peer).
- Other packages, including the internal `@peculiar/acme-*` and `@peculiar/jose` packages, are regular `dependencies`. Use the `@peculiar/utils` root or subpath entries, never `/legacy`.
- Internal ranges are bumped by the release pull request; don't change them by hand.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use the package directory as the scope for package-specific changes (for example `fix(server): ...`, `feat(client): ...`).

Mark breaking changes with `!` after the type or scope (for example `feat(server)!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `master`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration.
- Keep changes small and localized to the owning package.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). All packages share one version and are released together.

1. On every push to `master`, the **Release** workflow first runs lint, format, typecheck, tests, and build (the **Test** workflow). Only when they pass does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and every `packages/*/package.json` version, the internal `@peculiar/acme-*` and `@peculiar/jose` ranges, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release.
2. Merge the release pull request. release-please creates one `vX.Y.Z` tag and one GitHub Release with the notes from the pull request; the workflow then publishes every public package whose version is not on npm yet via Trusted Publisher, with provenance, dependencies first, and moves the major tag (for example `v2`) when this is the newest release of that major.

To retry a failed or partial npm publish, run **Release** manually from the `vX.Y.Z` tag; packages already on npm are skipped. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request. Every package needs an npm Trusted Publisher for this repository, workflow `release.yml` and environment `npm`.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/acme-ts/releases); there is no `CHANGELOG.md`. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description.
